# OmniBuild

Build, sign, install and ship iOS and Android apps with no native toolchain (no Xcode, no JDK, no Android SDK). A standalone Rust binary that repackages a prebuilt app shell with an app's config and assets, then signs it. Distributed through npm (one package per OS and CPU, as rspack and oxlint do), `cargo install`, Homebrew and GitHub releases. **Phase 0** (the spikes) of the plan in [issue #1](https://github.com/Blotch-Smart-Frames/omni-build/issues/1): `omni repackage` handles Android APK and AAB shells, and iOS shells built for the Simulator (signed ad hoc) or for devices (an `.ipa`, signed with the user's key and provisioning profile). Keys come from PKCS #12 keystores or PEM: `omni key create` makes Android upload keys, and `omni key request` and `key import` Apple signing keys, from a certificate signing request to the certificate Apple issues. `omni provision` gets the certificate and a provisioning profile for each bundle through App Store Connect's API with the user's API key (`packages/cli/src/app_store_connect.rs`, `ios/provisioning.rs`), over ureq and the same rustls and provider as wireless debugging. **Phase 1** has begun: `omni install` installs an APK over ADB, on a phone plugged in by USB (through nusb, the systems' own USB APIs in pure Rust), an emulator or a device on the network (TCP), with adb's own key from `~/.android/adbkey`, and `omni tcpip` has a phone plugged in listen for ADB on the network, as `adb tcpip` does. `omni pair` pairs with a phone for Android 11's wireless debugging, as `adb pair` does, with SPAKE2 as BoringSSL has it (`packages/cli/src/adb/spake2.rs`), and a device that asks for TLS (`STLS`) gets TLS 1.3 through rustls, with the pure-Rust provider rustls-rustcrypto (`adb/tls.rs`). **Phase 4** has begun too: `repackage` adds the native modules among the app's npm dependencies (`packages/cli/src/modules.rs`, then `ios/modules.rs` and `android/modules.rs`), prebuilt binaries a module declares under `omniBuild` in its `package.json` for the runtime the shell names (`OmniBuildRuntime` in `Info.plist`, `<meta-data android:name="dev.omnibuild.runtime">`), and lists them where the shell registers them by name. The Module workflow (`.github/workflows/module.yml`) builds a module's binaries for its author with the shells' tool (`packages/shells/src/module-*.ts`), and the E2E fixture shells name a runtime and register a module CI builds with it (`packages/e2e/fixtures/module`). The WebView shell's runtime is `webview@1`: its pages call native modules through `window.omniBuild` (`NativeModules.swift`, `NativeModules.kt`), which the E2E web app does with `fixtures/web-module`. With `--json`, every command reports its events as JSON lines on stdout for build tools (`packages/cli/src/report.rs`), which the npm package's `omniBuild()` reads and types (`packages/omni-build/src/index.ts`): the two change together.

**OmniBuild is framework-agnostic.** The frameworks that build apps with it are its users, so the code, docs, issues and PRs name none of them, their packages or their commands. Lynx and WebView apps appear only as examples of apps whose per-app part is data.

## Repository

An npm workspaces + turbo monorepo with the Rust inside `packages/` (see the README for the package table). The npm names are in Blotch's scope: `@blotch/omni-build` for the launcher and `@blotch/omni-build-<platform>-<arch>` for the platform packages. `@omni-build` is someone else's, and npm refuses an unscoped `omni-build` as too close to the `omnibuild` it has. The command they install, the binary Cargo builds, is `omni`, while the crate stays `omni-build` (`cargo install omni-build`). Things that aren't obvious from the files:

- **Each Rust crate is listed by path** in the root `Cargo.toml`'s `members`. A `packages/*` glob would also match the npm packages, which have no `Cargo.toml`, and Cargo would fail.
- **A Rust crate that turbo should run has a private `package.json`** whose scripts call Cargo (see `packages/cli`). Its turbo `build` and `test` aren't cached: Cargo caches them in the shared `target/`.
- **Platform packages aren't in the repository**, and the launcher's `package.json` doesn't list them. As workspaces, npm fails `npm install` with EBADPLATFORM on every machine but one. As `optionalDependencies` of an unpublished version, npm can't lock them and `npm ci` fails. `packages/omni-build/src/platforms.ts` is the list. `packages/release` packs them from it, with the launcher and its `optionalDependencies` (`pack`), and CI's `install` jobs install them on all six OSes and CPUs from a registry on the runner (`check`). The same jobs unpack each platform's archive for the GitHub release (`archive`, `check-archive`), the `homebrew` jobs install the formula for them (`formula`), and the `crate` job packages the crate as crates.io gets it. A `v<version>` tag releases what CI made for that commit to every channel (`.github/workflows/release.yml`): npm (`publish`), a GitHub release with the archives and the WebView shell, crates.io, and the Homebrew tap, `Blotch-Smart-Frames/homebrew-tap`. A maintainer approves it once, in the `npm` environment. npm and crates.io trust that workflow file and their environments (`npm`, `crates-io`) to publish, so there's no token for either, and renaming one means changing the trusted publisher there; the tap takes a deploy key the `homebrew` environment holds (the steps are in `packages/release/README.md`).
- **Versions move in lockstep:** `[workspace.package] version` in `Cargo.toml` and every `package.json`. The launcher's tests fail if `omni --version` differs from its `package.json`.

- **The npm packages are TypeScript, run without a build** wherever Node can: it strips the types from the private packages' `.ts` files (CI runs the e2e harness and the platform watch with no `npm ci`). So imports name the `.ts` file and only erasable syntax is allowed (`erasableSyntaxOnly` in `tsconfig.base.json`: no enums, namespaces or parameter properties). The launcher is compiled to `dist/`, because Node won't strip types under `node_modules`, and its tests run the compiled `dist/cli.js`. Node, vitest and Docusaurus all strip types without checking them, so `npm run typecheck` (CI's `typecheck` job) is the only type check.
- **Every `.ts` and `.tsx` module has a `.test.ts` or `.test.tsx` beside it** (tool configs such as `vitest.config.ts` aside), the e2e harness and the docs site's included: the harness's tests stand in for Xcode, Gradle, adb and simctl, and the docs' run in jsdom, the components with React Testing Library. A new module gets its test in the same change.
- **CI requires 100% test coverage** of lines, functions and regions or branches, in Rust (cargo-llvm-cov) and TypeScript (vitest thresholds). Code that can only run in a child process gets an in-process seam rather than an exclusion: in each npm package with a command, `cli.ts` is a few lines wiring `run.ts` to the process, and a `tests/` integration test running the binary covers `main()`.
- **100% must come from each module's own test.** `npm run test:coverage` ends with `packages/coverage-guard`, which runs every module's test on its own, measuring only that module, and fails if it doesn't cover all of it: a component a page renders is covered by the page's test, but only its own test checks it. It also fails on a module with no test beside it, a coverage-ignore comment (`v8`, `c8`, `istanbul`, `#[coverage(off)]`, `cfg(coverage)`), and a Rust file missing from cargo-llvm-cov's report. So never exclude code from coverage; test it, or give it a seam.
- **The USB tests only run on Linux.** `packages/cli/src/adb/usb.rs`'s tests plug made-up phones into vhci-hcd, Linux's virtual USB host controller, and answer the kernel as each phone over USB/IP, so the kernel's real USB stack sits between them and OmniBuild. CI's coverage job loads vhci-hcd and a udev rule for them. Other systems have no virtual USB, so there that file falls short of 100%: run its tests in Docker Desktop's Linux, which has vhci-hcd built in (the command is in the README).
- **The PR gate is the "CI passed" job** in `.github/workflows/ci.yml`, which needs every other job. Add new jobs to its `needs`.
- **E2E tests run in three stages** (`packages/e2e`): Xcode and Gradle build real Swift and Kotlin shells (only in our CI, never for users), OmniBuild repackages them on Linux, Windows and macOS with no `PATH` or toolchain variables, and the iOS Simulator and an Android emulator run every result. The fixture apps report their own ID, name, version, payload and icon on launch, so no UI driver is needed. A value OmniBuild learns to rewrite gets a field in both fixtures' reports.
- **The shells OmniBuild ships are in `packages/shells`** (the WebView shell, for web apps), and go through the same three E2E stages as the fixtures. CI builds both with the Shell workflow (`.github/workflows/shell.yml`), a reusable workflow frameworks call for their own shells: it builds every variant, debug and release, with `packages/shells/src` from OmniBuild at the commit it's called at, checks that omni repackages each, and writes their manifest of SHA-256s. A release attaches the WebView shell's to the GitHub release. Every shell, the fixtures included, keeps the same Android API levels, Android Gradle plugin and iOS deployment target: the platform watch reads the WebView shell's, and `packages/e2e/src/shell.test.ts` fails when another differs.
- **The platform watch** (`packages/platform-watch`) runs daily and opens an issue when the shells need a newer Xcode or Android API level, or when it can't download or parse one of Apple's or Google's pages. It reads the shells' toolchain from `DEVELOPER_DIR` in `ci.yml` and the WebView shell's `app/build.gradle.kts`, so moving either means updating `src/sources.ts`.

```sh
npm run build | test | lint | cspell | typecheck | format | format:check   # all packages, through turbo
npm run test:coverage                                             # then coverage-guard; needs cargo-llvm-cov installed
cargo run -- --help                                               # the binary, straight from Cargo
```

## Code Style

- Always write comments explaining **why** something is done, not just what. Future developers need to understand the reasoning and intent behind decisions, especially around undocumented or reverse-engineered formats (`Assets.car`) and store validation rules.

## Commits, PRs and Comments

- Never add AI attribution to commit messages, PR descriptions or code comments: no `Co-Authored-By` trailer, no "Generated with Claude Code" line, no mention of the AI tool or the company behind it. This overrides any default attribution instructions.
